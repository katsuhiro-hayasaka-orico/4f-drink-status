# 4Fドリンク速報

弘済ビル4Fラウンジのドリンクマシンの状態を、そこにいる人の投稿から推定して表示する掲示板です。

「コーヒー、まだある?」に答えるために4階まで上がらなくて済むように——という一点のためのアプリで、
投稿は**ログイン不要・2タップ**、集計は**利用者ごとの最新投稿を1票**として行います。

Vite + React + TypeScript のフロントエンドと、Cloudflare Workers + D1 のバックエンドで動作します。

---

## 動かす

初回だけ、依存の取得とローカルDBの用意が要ります。

```bash
npm install
npm run db:migrate:local    # ローカル D1 にスキーマを作る
npm run db:seed:local       # サンプル投稿を入れる（任意・何度でも実行可）
```

> `db:migrate:local` は `wrangler.toml` の `database_id` を見ません（ローカルのSQLiteを使う）ので、
> デプロイ前でもそのまま動きます。

起動は目的で使い分けます。

**動作を検証する（本番と同じ構成）**

```bash
npm run build
npm run dev:worker
```

→ http://localhost:8787 　Worker・D1・静的アセットまで含めて本番と同じ経路で動きます。

**UIを編集しながら見る（HMR）**

ターミナルを2つ使います。

```bash
npm run dev:worker    # 1つめ：APIとDB（8787番）
npm run dev           # 2つめ：Vite の開発サーバー
```

→ http://localhost:5173 　`/api` は 8787 にプロキシされます。保存すると即座に反映されます。

**注意**: `npm run dev:worker` はアセット一覧を起動時に読み込みます。`public/` にファイルを
足したときや `npm run build` をやり直したときは、Worker を再起動してください。

その他:

```bash
npm run typecheck   # アプリと Worker の両方を型チェック
npm test            # 集計・通知ロジックのユニットテスト
npm run build       # 型チェック → dist/client へビルド
```

## デプロイ

初回は次の1本で完了します（D1 の作成 → `wrangler.toml` への ID 書き込み → スキーマ適用 →
`SESSION_SECRET` の生成と登録 → ビルド → デプロイ）。何度実行しても同じ状態に収束します。

**macOS / Linux / Git Bash**

```bash
npx wrangler login          # ブラウザが開きます。ヘッドレス環境では代わりに
                            # CLOUDFLARE_API_TOKEN を設定してください
./scripts/setup-cloudflare.sh
```

**Windows（PowerShell）** — `.sh` は実行できないので同等の `.ps1` を使います。
既定の実行ポリシーは `.ps1` を拒否するため `-ExecutionPolicy Bypass` が必要です。

```powershell
npx wrangler login
powershell -ExecutionPolicy Bypass -File scripts\setup-cloudflare.ps1
```

> Windows PowerShell 5.1 は `&&` を解釈しません（PowerShell 7 以降の構文です）。
> このREADMEに `a && b` と書かれたコマンドは、2行に分けて実行してください。

2回目以降、コードだけを更新する場合は次で十分です。

```bash
npm run deploy
```

手動で行う場合は以下と同等です。

```bash
npx wrangler d1 create drink-status      # 出力された database_id を wrangler.toml に記入
npm run db:migrate:remote
npx wrangler secret put SESSION_SECRET   # 匿名IDクッキーの署名鍵（必須）
npm run deploy
```

`SESSION_SECRET` を設定しないと開発用の既定値が使われ、クッキーの署名を誰でも偽造できます。
本番では必ず設定してください。セットアップスクリプトは未設定の場合のみ、ランダムな32バイトを
生成して登録します。

### CI やヘッドレス環境からデプロイする場合

`wrangler login` は対話的な OAuth なので使えません。API トークンを環境変数で渡してください。

```bash
export CLOUDFLARE_API_TOKEN=...   # 履歴に残さないよう注意
./scripts/setup-cloudflare.sh
```

トークンに必要な権限（Cloudflare ダッシュボード → My Profile → API Tokens → Create Token →
Create Custom Token）:

| 種別 | 権限 | レベル |
| --- | --- | --- |
| Account | Workers Scripts | Edit |
| Account | D1 | Edit |
| Account | Account Settings | Read |

ネットワークが制限された環境では、`api.cloudflare.com` への外向き通信を許可する必要があります。

## 投稿できるもの

投稿は2種類あり、性質がまったく違うので集計も分かれています。

| 種類 | 対象 | 選ぶもの | 集計ウィンドウ |
| --- | --- | --- | --- |
| 在庫・状態 | コーヒー豆／ココア／ミルク／氷／マシン全体 | 取れた・残り少なめ・作れない・補充された | 30分 |
| 行列 | 行列 | 0人・1〜2人・3〜5人・6人以上 | **10分** |

型の上でも混ざりません。`isValidReportValue` が唯一の判定箇所で、API もクライアントもここを通るため、
行列に「補充された」、ココアに「6人以上」といった組み合わせは保存されません。

## 集計ルール

`shared/aggregate.ts` に実装、`shared/aggregate.test.ts` に全ルールのテストがあります。

### 在庫・状態

1. **過去30分の投稿だけ**を対象にします。
2. **「補充された」でリセット** — 補充より前の投稿は、いまの状態の証拠にはなりません。
3. **1人1票** — 同じ人の投稿は最新のものだけを数えます。
4. **新しい投稿ほど重い** — 10分以内は1.0、20分以内は0.7、30分以内は0.4。
   25分前の目撃談が、直近2件をひっくり返さないようにするためです。
5. **「作れない」が10分以内に2件以上あれば無条件で不可** — 空だという報告は、
   空でないという報告より重く扱います。ただし1件だけでは多数派を覆しません。

確からしさは投稿者数・一致率・鮮度の3つで決まります。

| | 条件 |
| --- | --- |
| 高 | 3人以上 ／ 一致率75%以上 ／ 最終観測10分以内 |
| 中 | 2人以上 ／ 一致率60%以上 ／ 最終観測20分以内 |
| 低 | 上記以外 |

材料の推定残量は投稿の種類に対応します（取れた 70% ／ 残り少なめ 30% ／ 作れない 0% ／ 補充された 100%）。

### 投稿が途切れたとき（情報なしと残照）

30分のウィンドウが空になったあと、**最後の投稿がいつまで画面に残るかは、その内容で変わります**。

- 最後の投稿が**「取れた」または「補充された」**なら、その良好状態を**2時間**
  （`availableRetentionMin`）まで保持します（残照）。在庫は勝手には消えないので、
  良い知らせはゆるやかに古びます。ただし確からしさは必ず「低」に落ち、
  最終観測時刻も正直にそのまま表示します。票数には数えません
  （「過去30分の有効観測」が2時間前の目撃を新しい証拠のように数えないため）。
- 最後の投稿が**「残り少なめ」または「作れない」**なら保持せず、30分で**「情報なし」**に
  戻ります。古くなった悪い知らせこそ再確認してほしい情報であり、何時間も人を
  遠ざけ続けるべきではないからです。
- どの投稿も2時間より古ければ**「情報なし」**です。以前は画面が空にならないよう
  デモ由来の既定値（75%／35%／80%など）を表示していましたが、誰も見ていない不足を
  自信ありげに報告してしまうため廃止しました。見た人がいないなら、ないと言います。

判断はつねに**最新の投稿1件**が下します。90分前の「取れた」があっても、40分前に
「残り少なめ」が出ていれば残照にはならず「情報なし」です。

### 行列

混雑はすぐ変わるため、在庫とは別のパラメータを使います。

- **ウィンドウは10分**。25分前の在庫情報にはまだ価値がありますが、25分前の行列情報は
  いま行くべきかの判断材料になりません。
- **減衰がずっと急** — 2分以内は1.0、5分以内は0.6、10分以内は0.3。
  8分前の投稿は在庫なら満点ですが、行列では0.3にしかなりません。
  結果として、**いま見た人ひとりが、少し前に見た数人に勝ちます**。
- **同点は混んでいる側に倒します**。空いていると誤って伝えるほうが実害が大きいためです。
- 確からしさは 高＝2人以上・一致率67%以上・最終観測3分以内、中＝一致率50%以上・5分以内。

待ち時間の目安は1杯あたり約45秒として算出した粗い範囲です。3分か4分かを当てる意味はなく、
いま行く価値があるかどうかだけが分かれば十分だからです。

## ドリンクと材料

実機のメニューのうち、熱湯とアメリカンを除いた8種を扱います。

| ドリンク | 必要な材料 |
| --- | --- |
| ホットコーヒー | コーヒー豆 |
| カフェラテ | コーヒー豆、ミルク |
| カフェモカ | コーヒー豆、ココア、ミルク |
| ホットココア | ココア |
| アイスコーヒー | コーヒー豆、氷 |
| アイスカフェラテ | コーヒー豆、ミルク、氷 |
| アイスカフェモカ | コーヒー豆、ココア、ミルク、氷 |
| アイスココア | ココア、氷 |

名前はマシンのボタンに合わせています。以前の「カフェオレ」は誤りで、マシンが淹れるのは
カフェラテです。並び順は コーヒー → ラテ → モカ → ココア で、ホットの行とアイスの行が
上下で対応します。

氷が切れるとアイス4種だけが落ち、ホットは影響を受けません。マシン全体が止まると全種が落ちます。
作れない場合は理由に不足している材料名を出します（例:「氷がありません」）。

カードにはドリンクの絵（ホットはマグと湯気、アイスはグラスと氷とストロー）を添えています。
これは飾りではなく、**カップの中身の量が状態に連動**します。作れます＝満杯、残り少なめ＝半分、
作れません＝空（さらに薄く表示）。文字を読まずに絵だけで一覧を把握できます。
液の色はドリンクごとに変えてあり、氷の粒は製氷機と同じ形です。

製氷機はマシンの絵の左隣に別ユニットとして描かれ、氷の粒が残量に応じて積み上がります。
4本目のタンクにしなかったのは、実物が別筐体であることに加え、既存の3タンク（特にコーヒー豆の
粒の描画）を作り直さずに済ませるためです。ドリンクマシン側は元の設計座標のまま
`MACHINE_SHIFT` ぶん右へ平行移動しているだけなので、並び順を変えても中身の座標は無傷です。

## 開放時間（9:00〜17:00）

画面は時刻に連動します。判定は `shared/hours.ts`、時刻は `shared/config.ts` の
`openHour` / `closeHour` です。

| 時刻 | ヘッダー | 概要パネル |
| --- | --- | --- |
| 9:00〜16:30 | 開放中 | 通常（マシンの状態） |
| 16:30〜17:00 | まもなく終了 | 通常＋「17:00に閉まります（あとN分）」 |
| 17:00〜翌9:00 | 時間外 | 「いまは閉まっています」＋次に開く時刻 |

時間外は「いまの状態」を扱うパネル（マシンの絵・推定残量・作成可否）を**すべて「情報なし」**に
します。誰も使えない時間帯に17:00時点の残量を現在形で示すのは不正確だからです。
履歴のセクション（みんなの観測・投稿の内訳）は実際の投稿をそのまま表示し続けます。

**時刻はJST固定**で、閲覧者の端末のタイムゾーンは見ません。ラウンジは東京の9:00に開くので、
端末が別のタイムゾーンに設定されているだけで「開放中」と表示されるのは誤りだからです。

閉店中も**投稿はできます**。補充は時間外に行われることがあり、「補充された」は
見かけたときに記録できるべきだからです。投稿欄には時間外である旨だけ表示します。

毎日9:00〜17:00として実装しています。平日限定にする場合は `loungeHours` が唯一の判定箇所です。

## ダークモード

既定はOSの設定に従い、ヘッダーの切り替えUIで上書きできます。
「端末の設定に合わせる／ライト／ダーク」の3状態です。2状態のトグルにしなかったのは、
「OSに従う」が既定であり、かつ一度切り替えたあと戻れなくなるためです。

選んだ設定は `localStorage` に保存しますが、**保存するのは選択そのもので、解決後の色ではありません**。
「端末の設定に合わせる」のまま日没でOSがダークに変わると、画面も追従します。

初回ペイント前に `index.html` のインラインスクリプトが `data-theme` を確定させます。
これがないと一瞬ライトで描画されてから反転し、ダーク環境ではダークモードがないより不快になります。

色は**役割**で名前が付いており（`--selected-bg`、`--on-status` など）、値だけが配色ごとに
切り替わります。これは名前と実際の色が配色間でずれるためです。たとえば選択中のチップは
ライトでは「ページで最も暗い面」ですが、ダークでは「最も明るい面」になり、その上の文字色も
クリームから黒へ反転します。`--espresso` のような色名のままでは表現できません。

イラストの扱いは2つに分かれます。

- **器**（ホッパー、製氷機、マシンの筐体）は配色に追従します。追従させないと暗い画面で白く光ります。
- **中身**（コーヒー豆、ココア、ミルク、氷、ドリンクの液体）は両方の配色で実物の色のままです。
  これは画面が報告している内容そのものなので、テーマの都合で変えるべきではありません。

例外はスポウト下のカップで、白い陶器なので暗い面でも明るいままにしています。筐体と同じ色に
すると穴のように見えたためです。

コントラストは両配色で実測し、本文・ラベル・状態色すべて WCAG AA を満たしています
（唯一 4.22:1 の大見出しは、34px以上・太字なので大きい文字の基準 3:1 が適用されます）。

投稿フォームの「対象を選択」には各対象のアイコンを付けています。絵文字は環境によって字形が
変わるため、すべてSVGで描いた塗りのシルエットです。ページ内の他の表現と揃えてあり（豆はホッパーの
豆山、氷は製氷機のキューブ、行列は待ち人数の人型）、選択時はチップの前景色・背景色に追従して
反転します。

## ブラウザ通知

ヘッダーの「通知」ボタンでONにすると、**他の人の投稿**をブラウザ通知でお知らせします。

- 通知は既存の**30秒ポーリングに乗って**届きます。つまり**タブを開いている間だけ**有効です
  （バックグラウンドタブでも届きます）。ONにすると自動更新も同時にONになります。
- **タブを見ている間でも通知します**。壁のダッシュボードのように常時表示して、バナーと音で
  気づく使い方を想定しています（当初は表示中を抑制していましたが、実運用の要望で外しました）。
- 1回のポーリングで複数の投稿が届いた場合は**1件に畳みます**。同じ `tag` を使うので、
  未読の通知が積み上がらず、新しいものが古いものを置き換えます。
- **自分の投稿は通知しません**。新着判定はIDの差分ではなくサーバー時刻の高水位標
  （watermark）で行うため、取り消しによる行の消滅や一覧の200件窓のスライドに影響されません。
  判定ロジックは `src/lib/notifyLogic.ts` にあり、ユニットテストで固定しています。
- 初回ONのときにブラウザの許可ダイアログが出ます。ブロックした場合はボタンが
  「通知 ブロック中」になり、解除はブラウザ側の設定（アドレスバーの鍵アイコン）からです。
- iOS の Safari はホーム画面に追加したPWA以外で Notification API を持たないため、
  その環境ではボタン自体を表示しません。

### 通知が出ないとき

1. **ONにした瞬間の確認通知は出ましたか？** 出ていなければアプリではなく OS／ブラウザ側です。
   Windows: 設定 → システム → 通知 で Chrome が許可されているか、**集中モード（応答不可）**が
   オフかを確認してください。macOS: システム設定 → 通知 → Chrome。
2. 確認通知は出るのに新着が出ない場合、通知センターに**古い通知が残っていないか**確認して
   ください（修正済み: かつて確認通知が新着と同じ `tag` を使っており、残っている限り後続が
   無音の置き換えになるバグがありました。現在は tag を分け、新着は `renotify` 付きです）。
3. **長時間裏に置いたタブ**は、Chrome のメモリセーバーに破棄されることがあります（戻ると
   再読み込みになる挙動がそれです）。破棄中は JS ごと止まるため通知も止まります。
   Chrome の設定 → パフォーマンス で、このサイトを「常にアクティブにするサイト」に追加すると
   回避できます。
4. バックグラウンドタブのタイマーはブラウザに間引かれますが、完全には止まりません
   （最悪でも約1分に1回）。通知が「遅れて」届くのはこのためです。

**ブラウザを完全に閉じていても届く通知**（Web Push）は未実装です。Service Worker、
購読情報のテーブル、VAPID鍵の管理、RFC 8291 の暗号化実装が必要になるため、
必要になった時点で別途取り組むのが妥当と判断しました。

## みんなの声（ご意見の収集）

投稿へのお礼を伝えるついでに、サイト自体への感想（改善点・困ったことなど）を集めます。

- **投稿確定後にお礼** — 取り消し猶予の5秒が取り消されずに終わった瞬間、
  「投稿ありがとうございます！」のトーストが約6秒表示されます。トーストには毎回
  「ご意見を聞かせてください」の小さなリンクが付きます（取り消した投稿には出ません）。
- **入力フォームの自動表示は7日に1回まで** — 送信した人・フォームを閉じた人には、
  以後7日間（`feedbackPromptCooldownDays`）フォームを勝手に開きません。判定は
  localStorage（`drink-status-feedback-prompted`）なので端末ごとです。トーストのリンクや
  「みんなの声」セクションの「ご意見を書く」ボタンからは、いつでも開けます。
- **入力は満足度（😊😐😞）＋任意の自由記述** — 満足度だけのワンタップ送信もできます。
  本文は500文字まで（`feedbackMaxLength`）。
- **公開といいね** — 感想はページ下部の「みんなの声」に公開され、誰でも♥を付けられます
  （1人1感想1回、もう一度押すと取り消し）。満足度だけの送信は他の人にはカードとして
  見せず、セクション上部の内訳（😊N・😐N・😞N）にだけ数えます（**本人にだけ**は
  カードが見え、編集・削除できます）。自分の投稿には「自分」バッジが付きます。
  公開APIレスポンスに利用者IDは含めず、「自分がいいね済みか」「自分の投稿か」は
  サーバー側で真偽値に畳んでいます。
- **自分の感想は後から編集・削除できます** — 自分のカードにだけ「編集」「削除」ボタンが
  出ます。編集すると満足度・本文を差し替えられ、カードに**「編集済み」**と表示されます
  （♥が付いた後に内容が変わったことを隠さないため。いいねは維持されます）。削除は
  誤タップ防止のため2段階（「削除」→「本当に削除する」、4秒で自動解除）で、いいねごと
  消えます。所有権はサーバー側で端末IDと照合し、他人の投稿への編集・削除リクエストは
  存在しないものと同じ404を返します。時間制限はありません — 状態の投稿と違って感想は
  観測ではなく意見なので、いつでも撤回・修正できるべきだからです。
- **スパム対策** — 感想の投稿は1端末につき1日5件まで（429）。不適切な投稿は管理者が
  削除できます:

  ```
  npx wrangler d1 execute drink-status --remote --command "SELECT id, body FROM feedback ORDER BY created_at DESC LIMIT 20"
  npx wrangler d1 execute drink-status --remote --command "DELETE FROM feedback WHERE id='対象のid'"
  ```

感想はリアルタイム性が不要なので30秒ポーリングには乗せず、ページ表示時に1回取得し、
送信・いいねのレスポンスに更新後の一覧を同梱して描画し直します。

## 利用者の識別

ログインはありません。初回アクセス時に Worker が端末ごとのランダムなIDを発行し、
**HMAC-SHA256 で署名した httpOnly クッキー**に入れて返します。この署名があるため、
クッキーを書き換えて他人になりすましたり、票を水増ししたりはできません
（署名が合わないIDは破棄され、新しいIDが発行されます）。

表示名は初回投稿時に「利用者A」「利用者B」…と自動で割り当てられ、自分の投稿だけは
「利用者（あなた）」と表示されます。個人を特定する情報は保存しません。

Cloudflare Access に切り替える場合、識別は `worker/identity.ts` の `resolveIdentity` に
閉じているので、そこで検証済みJWTを読むように変えれば済みます。

## API

| | |
| --- | --- |
| `GET /api/reports` | 直近24時間の投稿（最大200件）と、呼び出し元のIDおよびサーバー時刻 |
| `POST /api/reports` | 投稿する。本文は `{ subject, action }` |
| `DELETE /api/reports/:id` | 取り消す。**自分の投稿**を、**取り消し可能時間内**に限る |
| `GET /api/feedback` | みんなの声の最新30件（いいね数・自分のいいね/投稿フラグ・編集日時込み） |
| `POST /api/feedback` | 感想を送る。本文は `{ mood, body }`。1端末1日5件まで（超過は429） |
| `PUT /api/feedback/:id` | **自分の感想**を編集する。本文は `{ mood, body }`。他人の投稿は404 |
| `DELETE /api/feedback/:id` | **自分の感想**をいいねごと削除する。他人の投稿は404 |
| `POST /api/feedback/:id/like` | いいねのトグル。対象が無ければ404 |

投稿と取り消しは更新後の一覧も返すので、クライアントは往復1回で描画し直せます。
不正な `subject` / `action` は400、1分あたり20件を超える投稿は429を返します。
`action` は対象が `queue` のときだけ待ち人数（`empty`/`short`/`medium`/`long`）を受け付け、
それ以外では在庫の状態（`available`/`low`/`unavailable`/`refilled`）のみを受け付けます。

## 元のデザインとの違い

`project/4F Drink Status.dc.html` のプロトタイプを実装したものです。見た目は踏襲していますが、
以下は意図的に変えています。

- **保存先** — localStorage から D1 へ。投稿がラウンジ全体で共有されるようになりました。
- **投稿者** — 固定のダミーから、署名付き匿名IDへ。
- **「このアプリについて」の文面** — Azure 前提の記述を、実際の構成（Cloudflare）に合わせました。
- **デザインツールのツマミ** — マシンの絵の表示と集計ウィンドウは `shared/config.ts` の定数に固定。
  ヘッダーの自動更新 ON/OFF だけは操作できるままにしています。

ヘッダーの「デモ」バッジは `src/components/Header.tsx` の `BADGE` を `null` にすると消えます。
