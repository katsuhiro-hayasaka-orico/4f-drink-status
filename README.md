# 4Fドリンク速報

弘済ビル4Fラウンジのドリンクマシンの状態を、そこにいる人の投稿から推定して表示する掲示板です。

「コーヒー、まだある?」に答えるために4階まで上がらなくて済むように——という一点のためのアプリで、
投稿は**ログイン不要・2タップ**、集計は**利用者ごとの最新投稿を1票**として行います。

Vite + React + TypeScript のフロントエンドと、Cloudflare Workers + D1 のバックエンドで動作します。

---

## 動かす

初回だけ、依存の取得とローカルDBの用意が要ります。

```bash
npm install
npm run db:migrate:local    # ローカル D1 にスキーマを作る
npm run db:seed:local       # サンプル投稿を入れる（任意・何度でも実行可）
```

> `db:migrate:local` は `wrangler.toml` の `database_id` を見ません（ローカルのSQLiteを使う）ので、
> デプロイ前でもそのまま動きます。

起動は目的で使い分けます。

**動作を検証する（本番と同じ構成）**

```bash
npm run build
npm run dev:worker
```

→ http://localhost:8787 　Worker・D1・静的アセットまで含めて本番と同じ経路で動きます。

**UIを編集しながら見る（HMR）**

ターミナルを2つ使います。

```bash
npm run dev:worker    # 1つめ：APIとDB（8787番）
npm run dev           # 2つめ：Vite の開発サーバー
```

→ http://localhost:5173 　`/api` は 8787 にプロキシされます。保存すると即座に反映されます。

**注意**: `npm run dev:worker` はアセット一覧を起動時に読み込みます。`public/` にファイルを
足したときや `npm run build` をやり直したときは、Worker を再起動してください。

その他:

```bash
npm run typecheck   # アプリと Worker の両方を型チェック
npm test            # 集計・通知ロジックのユニットテスト
npm run build       # 型チェック → dist/client へビルド
```

## デプロイ

初回は次の1本で完了します（D1 の作成 → `wrangler.toml` への ID 書き込み → スキーマ適用 →
`SESSION_SECRET`・`VAPID_PRIVATE_JWK` の生成と登録 → ビルド → デプロイ）。
何度実行しても同じ状態に収束します。

**macOS / Linux / Git Bash**

```bash
npx wrangler login          # ブラウザが開きます。ヘッドレス環境では代わりに
                            # CLOUDFLARE_API_TOKEN を設定してください
./scripts/setup-cloudflare.sh
```

**Windows（PowerShell）** — `.sh` は実行できないので同等の `.ps1` を使います。
既定の実行ポリシーは `.ps1` を拒否するため `-ExecutionPolicy Bypass` が必要です。

```powershell
npx wrangler login
powershell -ExecutionPolicy Bypass -File scripts\setup-cloudflare.ps1
```

> Windows PowerShell 5.1 は `&&` を解釈しません（PowerShell 7 以降の構文です）。
> このREADMEに `a && b` と書かれたコマンドは、2行に分けて実行してください。

2回目以降、コードだけを更新する場合は次で十分です。

```bash
npm run deploy
```

手動で行う場合は以下と同等です。

```bash
npx wrangler d1 create drink-status         # 出力された database_id を wrangler.toml に記入
npm run db:migrate:remote
npx wrangler secret put SESSION_SECRET      # 匿名IDクッキーの署名鍵（必須）
npm run vapid                               # Web Push の鍵ペアを生成して表示
npx wrangler secret put VAPID_PRIVATE_JWK   # ↑で表示された秘密鍵 JWK を貼り付け
npm run deploy
```

`SESSION_SECRET` を設定しないと開発用の既定値が使われ、クッキーの署名を誰でも偽造できます。
本番では必ず設定してください。セットアップスクリプトは未設定の場合のみ、ランダムな32バイトを
生成して登録します。`VAPID_PRIVATE_JWK` はプッシュ通知の署名鍵で、未設定でもサイトは動きます
（通知ボタンが隠れるだけ）。詳細は「プッシュ通知（Web Push）」の章を参照してください。

### CI やヘッドレス環境からデプロイする場合

`wrangler login` は対話的な OAuth なので使えません。API トークンを環境変数で渡してください。

```bash
export CLOUDFLARE_API_TOKEN=...   # 履歴に残さないよう注意
./scripts/setup-cloudflare.sh
```

トークンに必要な権限（Cloudflare ダッシュボード → My Profile → API Tokens → Create Token →
Create Custom Token）:

| 種別 | 権限 | レベル |
| --- | --- | --- |
| Account | Workers Scripts | Edit |
| Account | D1 | Edit |
| Account | Account Settings | Read |

ネットワークが制限された環境では、`api.cloudflare.com` への外向き通信を許可する必要があります。

## 投稿できるもの

投稿は**ドリンク起点**です。利用者の実体験は「カフェモカを作れた／作れなかった」であり、
材料の残量はそこからサーバーが導出します（`shared/drinkReport.ts` の展開ルール）。

| 種類 | 入力 | 展開される票 | 集計ウィンドウ |
| --- | --- | --- | --- |
| ドリンク報告 | ドリンク8種 ×「問題なく作れた／作れたが残り少なそう（材料を任意申告）／作れなかった（原因を必ず申告）」 | 下表参照 | 30分 |
| 補充報告 | 材料4種の「補充を見かけた」 | その材料に `補充された`（100%） | 30分 |
| 残量の目撃報告 | 材料4種の「残りが少なそうだと気づいたら」 | その材料に `残り少なめ` | 30分 |
| マシン自体 | 「故障中」「清掃中」「復旧した」の専用ボタン | マシン全体に `作れない`／`清掃中`／`補充された` | 30分 |
| 行列 | 0人・1〜2人・3〜5人・6人以上（**行列パネル内**の別入力。ドリンク投稿直後のフォローアップからも1タップ） | 行列に人数帯 | **10分** |

残量の目撃報告は、ご意見箱の「自分は作らなかったが、直前の人の氷がほとんど出ていなかった —
そういう目撃も反映したい」という声を受けて追加したものです。補充報告と同じ**目撃ベース**の
直接投稿で、推測ではなく見たものを報告する窓口なので、ドリンク起点の設計（原因不明の失敗が
材料票をばらまかない）とは矛盾しません。「なくなっていた」の直接投稿は意図的に設けていません
— 枯渇の断定は実際に作ろうとした人の失敗報告（原因の名指し）に任せ、目撃者は「少なそう」まで、
という役割分担です。

**展開ルール** — 1回のドリンク投稿は複数の票に展開され、同じグループIDで保存されます
（取り消しはグループ一括）:

| 投稿内容 | 展開 |
| --- | --- |
| 作れた | 使った材料すべてに「十分にある」＋マシンに「利用できる」＋ドリンク行「作れた」 |
| 作れた＋残り少なめ申告 | 申告材料は「残り少なめ」、残りは「十分にある」＋マシンOK＋「作れた」 |
| 作れなかった（原因=材料X） | X にだけ「なくなっている」＋「作れなかった」。**他の材料には票を入れません** |
| 作れなかった（原因=マシン） | マシンに「作れない」＋「作れなかった」 |
| 作れなかった（原因=わからない） | ドリンク行「作れなかった」のみ。**推測で材料を疑いません**（可否カードにだけ反映） |

成功は使った材料すべての保証になりますが、失敗は名指しされた犯人しか疑わない — この非対称が
設計の核です。原因不明の失敗が材料票をばらまくと、ボードが推測で汚染されるためです。

**清掃中はマシン専用の第3の状態**です。補充作業の直後に清掃の札が立ち、しばらくマシン全体が
使えない — という実運用の観察から追加しました。集計上は「利用不可」として数えますが、故障とは
別のメッセージとして表示します: 見出しは赤の「いまは使えません」ではなくオレンジの
「お掃除中です（終わればまた使えます）」、可否カードの理由も
「お掃除中です。終わればまた作れます」。清掃と故障の報告が両方ある場合は、新しい方の報告が文言を決めます。
値の検証は他と同じく `isValidReportValue` が唯一の判定箇所で、材料や行列に「清掃中」は
保存できません。

**ドリンクの人気度** — ドリンク報告の**全期間累計**をランキング表示します（「作れた」＋
「作れなかった」の合計で降順）。直近24時間しか持たない投稿一覧とは別に、サーバー側で
`GROUP BY` した累計を `GET /api/reports` に同梱しています。バーは 作れた／作れなかった の
2セグメント積み上げで、赤緑色覚でも判別できるよう「作れなかった」側には斜線テクスチャを
敷いています（色のみに頼らない・凡例に✓/×記号・行ごとに読み上げテキストあり）。

**投稿の内訳テーブルは投稿単位**で表示します。展開された材料・マシンの票は集計にだけ使い、
履歴には「アイスコーヒー／作れた」の1行だけを載せます（派生行を並べるのは過剰なため）。
プッシュ通知も同様に、1回のドリンク投稿を1件として文面にします。

型の上でも混ざりません。ドリンク報告は `parseDrinkReport` が唯一の判定箇所で、レシピ外の材料を
「残り少なめ」に申告したり、原因なしの失敗を投稿したりはできません。単票は従来どおり
`isValidReportValue` を通ります。

## 集計ルール

`shared/aggregate.ts` に実装、`shared/aggregate.test.ts` に全ルールのテストがあります。

### 在庫・状態

1. **過去30分の投稿だけ**を対象にします。
2. **「補充された」でリセット** — 補充より前の投稿は、いまの状態の証拠にはなりません。
3. **1人1票** — 同じ人の投稿は最新のものだけを数えます。
4. **新しい投稿ほど重い** — 10分以内は1.0、20分以内は0.7、30分以内は0.4。
   25分前の目撃談が、直近2件をひっくり返さないようにするためです。
5. **「作れない」が10分以内に2件以上あれば無条件で不可** — 空だという報告は、
   空でないという報告より重く扱います。ただし1件だけでは多数派を覆しません。

確からしさは投稿者数・一致率・鮮度の3つで決まります。

| | 条件 |
| --- | --- |
| 高 | 3人以上 ／ 一致率75%以上 ／ 最終観測10分以内 |
| 中 | 2人以上 ／ 一致率60%以上 ／ 最終観測20分以内 |
| 低 | 上記以外 |

材料の推定残量は投稿の種類に対応します（取れた 70% ／ 残り少なめ 30% ／ 作れない 0% ／ 補充された 100%）。

### 投稿が途切れたとき（情報なしと残照）

30分のウィンドウが空になったあと、**最後の投稿がいつまで画面に残るかは、その内容で変わります**。

- 最後の投稿が**「取れた」または「補充された」**なら、その良好状態を**2時間**
  （`availableRetentionMin`）まで保持します（残照）。在庫は勝手には消えないので、
  良い知らせはゆるやかに古びます。ただし確からしさは必ず「低」に落ち、
  最終観測時刻も正直にそのまま表示します。票数には数えません
  （「過去30分の有効観測」が2時間前の目撃を新しい証拠のように数えないため）。
- 最後の投稿が**「残り少なめ」または「作れない」**なら保持せず、30分で**「情報なし」**に
  戻ります。古くなった悪い知らせこそ再確認してほしい情報であり、何時間も人を
  遠ざけ続けるべきではないからです。
- どの投稿も2時間より古ければ**「情報なし」**です。以前は画面が空にならないよう
  デモ由来の既定値（75%／35%／80%など）を表示していましたが、誰も見ていない不足を
  自信ありげに報告してしまうため廃止しました。見た人がいないなら、ないと言います。

判断はつねに**最新の投稿1件**が下します。90分前の「取れた」があっても、40分前に
「残り少なめ」が出ていれば残照にはならず「情報なし」です。

### 行列

混雑はすぐ変わるため、在庫とは別のパラメータを使います。

- **ウィンドウは10分**。25分前の在庫情報にはまだ価値がありますが、25分前の行列情報は
  いま行くべきかの判断材料になりません。
- **減衰がずっと急** — 2分以内は1.0、5分以内は0.6、10分以内は0.3。
  8分前の投稿は在庫なら満点ですが、行列では0.3にしかなりません。
  結果として、**いま見た人ひとりが、少し前に見た数人に勝ちます**。
- **同点は混んでいる側に倒します**。空いていると誤って伝えるほうが実害が大きいためです。
- 確からしさは 高＝2人以上・一致率67%以上・最終観測3分以内、中＝一致率50%以上・5分以内。

待ち時間の目安は1杯あたり約45秒として算出した粗い範囲です。3分か4分かを当てる意味はなく、
いま行く価値があるかどうかだけが分かれば十分だからです。

## ドリンクと材料

実機のメニューのうち、熱湯とアメリカンを除いた8種を扱います。

| ドリンク | 必要な材料 |
| --- | --- |
| ホットコーヒー | コーヒー豆 |
| カフェラテ | コーヒー豆、ミルク |
| カフェモカ | コーヒー豆、ココア、ミルク |
| ホットココア | ココア |
| アイスコーヒー | コーヒー豆、氷 |
| アイスカフェラテ | コーヒー豆、ミルク、氷 |
| アイスカフェモカ | コーヒー豆、ココア、ミルク、氷 |
| アイスココア | ココア、氷 |

名前はマシンのボタンに合わせています。以前の「カフェオレ」は誤りで、マシンが淹れるのは
カフェラテです。並び順は コーヒー → ラテ → モカ → ココア で、ホットの行とアイスの行が
上下で対応します。

氷が切れるとアイス4種だけが落ち、ホットは影響を受けません。マシン全体が止まると全種が落ちます。
作れない場合は理由に不足している材料名を出します（例:「氷がありません」）。

カードにはドリンクの絵（ホットはマグと湯気、アイスはグラスと氷とストロー）を添えています。
これは飾りではなく、**カップの中身の量が状態に連動**します。作れます＝満杯、残り少なめ＝半分、
作れません＝空（さらに薄く表示）。文字を読まずに絵だけで一覧を把握できます。
液の色はドリンクごとに変えてあり、氷の粒は製氷機と同じ形です。

製氷機はマシンの絵の左隣に別ユニットとして描かれ、氷が残量に応じて溜まります。4本目のタンクに
しなかったのは、実物が別筐体だからです。

### マシンの絵は実機（WMF 1100 S）に寄せています

`src/components/MachineIllustration.tsx` はラウンジの実機の写真をもとに描いています。白いサイド
パネルに挟まれた黒い中央カラム、縦型のタッチディスプレイ、二股の吐出ノズル、凹んだカップ
ステーションとステンレスの受け皿格子、下部の台座。タッチパネルには実際に集計対象としている
8種（HOT 4種・ICE 4種）を並べています。名称は `DRINK_LABELS` から引いているので、隣の
「ドリンクの作成可否」カードと表記がずれることはありません。

実物と意図的に変えている点が2つあります。

- **ホッパーを上面に出して透明にしています。** 実機のホッパーは筐体内にあって正面からは見えま
  せんが、この絵の存在意義は「まだある？」に数字を読む前に答えることなので、残量が見える窓に
  誇張しました。
- **WMF のロゴは描いていません**（形と色は実機、ロゴは先方のものです）。

配色は `--wmf-*` トークンで切り替えます。実機の筐体は本当に黒に近いグレーなので、暗い画面では
そのまま描くと背景に沈みます。ダークモードだけシェルの明度を一段上げ、輪郭線を明るいグレーに
することで、黒いマシンのまま形が残るようにしています。ホッパーの中身（豆・粉・氷）とカップの
白磁は、どちらの配色でも実物の色のままです。

## 開放時間（9:00〜17:00）

画面は時刻に連動します。判定は `shared/hours.ts`、時刻は `shared/config.ts` の
`openHour` / `closeHour` です。

| 時刻 | ヘッダー | 概要パネル |
| --- | --- | --- |
| 9:00〜16:30 | 開放中 | 通常（マシンの状態） |
| 16:30〜17:00 | まもなく終了 | 通常＋「17:00に閉まります（あとN分）」 |
| 17:00〜翌9:00 | 時間外 | 「いまは閉まっています」＋次に開く時刻 |

時間外は「いまの状態」を扱うパネル（マシンの絵・推定残量・作成可否）を**すべて「情報なし」**に
します。誰も使えない時間帯に17:00時点の残量を現在形で示すのは不正確だからです。
履歴のセクション（みんなの観測・投稿の内訳）は実際の投稿をそのまま表示し続けます。

**時刻はJST固定**で、閲覧者の端末のタイムゾーンは見ません。ラウンジは東京の9:00に開くので、
端末が別のタイムゾーンに設定されているだけで「開放中」と表示されるのは誤りだからです。

閉店中も**投稿はできます**。補充は時間外に行われることがあり、「補充された」は
見かけたときに記録できるべきだからです。投稿欄には時間外である旨だけ表示します。

毎日9:00〜17:00として実装しています。平日限定にする場合は `loungeHours` が唯一の判定箇所です。

## ダークモード

既定はOSの設定に従い、ヘッダーの切り替えUIで上書きできます。
「端末の設定に合わせる／ライト／ダーク」の3状態です。2状態のトグルにしなかったのは、
「OSに従う」が既定であり、かつ一度切り替えたあと戻れなくなるためです。

選んだ設定は `localStorage` に保存しますが、**保存するのは選択そのもので、解決後の色ではありません**。
「端末の設定に合わせる」のまま日没でOSがダークに変わると、画面も追従します。

初回ペイント前に `index.html` のインラインスクリプトが `data-theme` を確定させます。
これがないと一瞬ライトで描画されてから反転し、ダーク環境ではダークモードがないより不快になります。

色は**役割**で名前が付いており（`--selected-bg`、`--on-status` など）、値だけが配色ごとに
切り替わります。これは名前と実際の色が配色間でずれるためです。たとえば選択中のチップは
ライトでは「ページで最も暗い面」ですが、ダークでは「最も明るい面」になり、その上の文字色も
クリームから黒へ反転します。`--espresso` のような色名のままでは表現できません。

イラストの扱いは2つに分かれます。

- **器**（ホッパー、製氷機、マシンの筐体）は配色に追従します（`--wmf-*`）。ただし追従の向きは
  実機色に合わせて反転していて、ダークでは**明るく**します — 実機が黒いので、暗い画面でそのまま
  描くと背景に沈むためです。
- **中身**（コーヒー豆、ココア、ミルク、氷、ドリンクの液体）は両方の配色で実物の色のままです。
  これは画面が報告している内容そのものなので、テーマの都合で変えるべきではありません。

例外はスポウト下のカップで、白い陶器なので両方の配色で白磁のままにしています。暗い面用に
くすませると、照明のないカップステーションの中で汚れて見えたためです。

コントラストは両配色で実測し、本文・ラベル・状態色すべて WCAG AA を満たしています
（唯一 4.22:1 の大見出しは、34px以上・太字なので大きい文字の基準 3:1 が適用されます）。

投稿フォームの「対象を選択」には各対象のアイコンを付けています。絵文字は環境によって字形が
変わるため、すべてSVGで描いた塗りのシルエットです。ページ内の他の表現と揃えてあり（豆はホッパーの
豆山、氷は製氷機のキューブ、行列は待ち人数の人型）、選択時はチップの前景色・背景色に追従して
反転します。

## プッシュ通知（Web Push）

ヘッダーの「通知」ボタンでONにすると、**他の人の投稿**をプッシュ通知でお知らせします。
**タブやブラウザを閉じていても届きます** — 以前の「30秒ポーリングに乗せるタブ内通知」は
廃止し、サーバーが投稿確定時に各ブラウザの push サービス（APNs / FCM / Mozilla autopush）
へ直接送る方式になりました。

### 仕組み

- 送信は Worker 上の**自前実装**です（`worker/push.ts`）。RFC 8291（aes128gcm 暗号化）と
  RFC 8292（VAPID 署名）を WebCrypto だけで実装しており、依存パッケージも外部ベンダー
  契約も不要です。**Cloudflare 無料プランの範囲内**で動きます（Queues 等の有料機能は不使用。
  1投稿あたりの送信数は subrequest 上限に収まるよう30件で頭打ちにしています）。
- 購読情報（endpoint と暗号鍵2つ）は D1 の `push_subscriptions` に保存します。endpoint が
  主キーで1ブラウザ=1行、1利用者（匿名ID）あたり8件まで（超えると古いものから整理）。
- **送信は投稿の約21秒後**です。取り消し（undo）の猶予が切れるまで `ctx.waitUntil` 内で
  待ち、投稿がまだ存在することを確認してから送ります。通知だけは取り消せないので、
  取り消せなくなるまで送らない、という順序です。
- **自分の投稿は自分に通知されません**（同じ匿名IDの購読を除外します）。
- ドリンク投稿は複数行に展開されますが、通知は**ドリンク行だけを1件**として文面にします
  （「利用者Bさんが カフェモカ「作れた」と投稿しました」）。
- 同じ `tag`＋`renotify` で表示するため、未読が積み上がらず、新しい通知が古いものを
  音付きで置き換えます。
- push サービスが 404/410 を返した購読（アンインストール・許可取り消し）は自動削除します。
- Service Worker（`public/sw.js`）は**通知の表示専用**です。fetch ハンドラもキャッシュも
  持たせていないため、オフライン表示などの副作用はありません。

### 端末ごとの注意

- **iPhone / iPad**: Safari の共有メニュー →「ホーム画面に追加」でインストールし、
  ホーム画面のアイコンから開くと「通知」ボタンが現れます（iOS 16.4以降）。ブラウザの
  タブでは iOS の仕様により Push API 自体が無効のため、ボタンは表示されません
  （サイト内「このアプリについて」にも同じ案内があります）。
- **Android**: Chrome のタブからそのままONにできます（インストール不要）。
- ブロックしてしまった場合はボタンが「通知 ブロック中」になり、解除はブラウザ側の設定
  （アドレスバーの鍵アイコン）からです。

### サーバー側の設定（VAPID 鍵）

Web Push には VAPID 鍵ペアが必要です。`scripts/setup-cloudflare.(sh|ps1)` が未設定なら
自動生成して secret に登録します。手動で行う場合:

```bash
npm run vapid                                # 鍵ペアを生成して表示
npx wrangler secret put VAPID_PRIVATE_JWK    # 表示された秘密鍵 JWK を貼り付け
```

- 秘密鍵は **wrangler secret のみ**に置きます（リポジトリは public なのでコードや設定
  ファイルには置きません）。
- ローカル開発では `.dev.vars`（git 管理外）に `VAPID_PRIVATE_JWK=...` を書きます。
- 未設定の間は `GET /api/push/key` が `null` を返し、通知ボタンは自動的に隠れます。
  それ以外の機能は通常どおり動きます。
- **鍵を作り直すと既存の購読は全て無効**になり、全員が通知をONにし直すことになります。
  setup スクリプトが既存の鍵を上書きしないのはこのためです。
- 送信者の連絡先（VAPID `sub`）は既定でこのリポジトリのURLです。変更する場合は
  wrangler.toml の `[vars]` に `VAPID_SUBJECT = "mailto:you@example.com"` を追加します。

### 管理者からのお知らせ配信

アップデートの告知などを、通知ONの全端末へ手動でプッシュ配信できます。
機械の状態通知とは別の通知スロット（tag）を使うので、互いに上書きしません。

認証トークンは**配信のたびに使い捨てで発行**します。控えの管理が不要になり、
画面への写り込み事故も起きません。プロンプトへの手貼りは不可視文字（改行など）が
混入して「Success なのに認証が通らない」事故のもとになるため、**変数＋パイプで
サーバーと手元に同じ値を渡す**のがポイントです:

```powershell
# D1用トークンが残っていると secret put が失敗するため先に掃除
Remove-Item Env:CLOUDFLARE_API_TOKEN -ErrorAction SilentlyContinue

$tok = node -e "process.stdout.write(require('crypto').randomBytes(24).toString('base64url'))"
$tok | npx wrangler secret put ANNOUNCE_TOKEN     # 「Success! Uploaded secret」を確認
$env:ANNOUNCE_TOKEN = $tok
$env:SITE_URL = "https://<デプロイURL>"
npm run announce -- "アップデート: 「いつ切れやすい？」マップを追加しました" --title "見出し（任意）"
Remove-Item Env:ANNOUNCE_TOKEN; Remove-Variable tok
```

`--title` 省略時の通知タイトルは「4Fドリンク速報」。本文は200文字までです。
エンドポイント（`POST /api/push/announce`）はトークン不一致・未設定時には 404 を
返し、存在自体を明かしません。認証だけ確かめたいときは、本文を空にして叩くと
トークンが正しい場合のみ 400（本文は1〜200文字…）に変わるので切り分けられます。

### デプロイ後の実機確認

暗号化と VAPID はユニットテストで固定しています（`worker/push.test.ts` — 独立実装の
受信側での復号ラウンドトリップ、ワイヤ構造の全フィールド検証、WebCrypto による JWT 検証）。
最後の一区間 — 本物の push サービスとの相互運用 — は実機でだけ確認できます:

1. 端末Aで通知をON → 「通知をONにしました…」の確認通知が出ること
2. 端末Aのタブ（iOSならアプリ）を**完全に閉じる**
3. 別の端末Bで何か投稿する
4. **約21秒後**、端末Aに通知が届くこと。タップするとサイトが開くこと

### 通知が出ないとき

1. **ONにした瞬間の確認通知は出ましたか？** 出ていなければアプリではなく OS 側です。
   Windows: 設定 → システム → 通知（集中モードもオフに）。macOS: システム設定 → 通知。
   iOS: 設定 → 通知 → 4Fドリンク。
2. 確認通知は出るのに新着が来ない場合 — 投稿から**約21秒**待ちましたか？ その投稿は
   すぐ取り消されていませんか？ **自分の投稿は届きません**。
3. iPhone は**ホーム画面のアイコンから**起動した状態でONにしましたか？ Safari のタブから
   ではボタン自体が出ません。低電力モードでは配送が遅れることがあります。
4. 長期間開かないと push サービス側が購読を失効させることがあります。その購読には
   サーバーが配送失敗（404/410）を検知した時点で自動的に整理されるため、
   通知ボタンを一度OFF→ONし直すと復活します。

## UI/UX 監査対応（2026-08）

外部の UI/UX アセスメントを受けて、次を変更しています。

- **投稿導線をファーストビューへ** — 監査の最重要指摘は「投稿欄が約1.6画面分下にあり、
  ページが閲覧専用に見える」でした。投稿セクションは概況の直後へ移動し、ヒーローに
  Primary CTA「＋ 今の状態を投稿する」を常設。投稿欄が画面外のときは右下に浮動の
  「＋ 投稿する」（スマホ幅では下部固定の全幅CTA）が出ます。CTA は投稿欄へスクロールし、
  先頭の対象チップへフォーカスを移します。
- **見出しと確からしさの整合** — 見出しの断定と「確からしさ：低」「ココア：情報なし」の同居が
  矛盾して見える問題。確からしさピルを見出しの同一行に移し、未報告の材料があるときは補足行で
  「ココア・氷はまだわかりません」と名指しして、主張の範囲をデータに合わせます。
- **対象は未選択スタート** — 以前は「コーヒー豆」が選択済みで、別対象のつもりで状態
  ボタンを先に押すとコーヒー豆として誤投稿されました。いまは対象を選ぶまで状態ボタンは
  無効で、選ぶと STEP2 の見出しに対象名が入ります（「**ミルク**の状態を選択して投稿」）。
- **状態ラベルを対象別に** — 材料は「十分にある／残り少なめ／なくなっている／補充された」、
  マシン全体は「正常に使えた／調子が悪い／使えない・故障／復旧した」。保存値・集計は不変で、
  ボタンの文言だけが対象に合わせて変わります（`actionLabelFor`）。
- **ドリンク可否は要約＋折りたたみ** — 8枚のカードは投稿前の情報過多の主因だったため、
  「いま作れます 2種・情報なし 6種」の1行要約を常時表示し、カードは開閉式（既定は閉）に。
- **アクセシビリティ** — 12px の補助文を 14px・`--body-text` へ（WCAG AA 4.5:1 以上）。
  テーマ切替ボタンを 40×36px へ拡大。可視テキストと同じ数値を読み上げていた一致度・残量
  メーターを装飾（aria-hidden）に変更。「みんなの観測」全体を包んでいた `aria-live` を
  廃止し、見出しの結論1行だけの不可視ライブリージョンに縮小。

### 簡易計測

監査の指標（CTA発見率・投稿完了率・取り消し率・初回投稿までの秒数）を測るため、
匿名イベントを D1 の `events` テーブルに記録します。イベント名は許可リスト
（`cta_click`＝CTAタップ／`report_view`＝投稿欄の初回表示／`post_done`＝投稿確定、
value にページ表示からの秒数／`post_undone`＝取り消し）だけで、自由記述は一切
保存しません。端末IDは投稿と同じ匿名IDです。閲覧APIは無く、集計は wrangler で行います:

```
# 日別のイベント件数とユニーク端末
npx wrangler d1 execute drink-status --remote --command "SELECT date(created_at/1000,'unixepoch') AS day, name, COUNT(*) AS n, COUNT(DISTINCT user_id) AS people FROM events GROUP BY day, name ORDER BY day DESC"

# 投稿完了率（post_done 人数 ÷ report_view 人数）や取り消し率、
# 初回投稿までの秒数は post_done の value を見ます
npx wrangler d1 execute drink-status --remote --command "SELECT COUNT(*) AS n, AVG(value) AS avg_sec FROM events WHERE name='post_done'"
```

## 利用者の識別

ログインはありません。初回アクセス時に Worker が端末ごとのランダムなIDを発行し、
**HMAC-SHA256 で署名した httpOnly クッキー**に入れて返します。この署名があるため、
クッキーを書き換えて他人になりすましたり、票を水増ししたりはできません
（署名が合わないIDは破棄され、新しいIDが発行されます）。

表示名は初回投稿時に「利用者A」「利用者B」…と自動で割り当てられ、自分の投稿だけは
「利用者（あなた）」と表示されます。個人を特定する情報は保存しません。

Cloudflare Access に切り替える場合、識別は `worker/identity.ts` の `resolveIdentity` に
閉じているので、そこで検証済みJWTを読むように変えれば済みます。

## API

| | |
| --- | --- |
| `GET /api/reports` | 直近24時間の投稿（最大200件）と、呼び出し元のIDおよびサーバー時刻 |
| `POST /api/reports/drink` | ドリンク報告。本文は `{ drink, result, low?, cause? }`。展開された票をグループで保存し `groupId` を返す |
| `DELETE /api/reports/group/:gid` | ドリンク報告の取り消し（グループ一括）。本人・取り消し可能時間内に限る |
| `POST /api/reports` | 単票の投稿（補充・マシン故障/復旧・行列）。本文は `{ subject, action }` |
| `DELETE /api/reports/:id` | 単票の取り消し。**自分の投稿**を、**取り消し可能時間内**に限る |
| `GET /api/feedback` | 満足度の集計（😊N・😐N・😞N）のみ。**本文は返さない** |
| `POST /api/feedback` | 感想を送る。本文は `{ mood, body }`。1端末1日5件まで（超過は429） |
| `POST /api/events` | 利用イベントを記録。本文は `{ name, value? }`。許可リスト外は400 |
| `GET /api/reports/rhythm` | 直近4週間の曜日×時間帯の投稿集計（「いつ切れやすい？」カード用の生データ） |
| `GET /api/push/key` | Web Push の公開鍵（applicationServerKey）。未設定なら `null` |
| `POST /api/push/subscribe` | 通知の購読登録。本文は `{ endpoint, p256dh, auth }`。形式不正は400 |
| `POST /api/push/unsubscribe` | 購読解除。本文は `{ endpoint }`。冪等（未登録でも200） |

投稿と取り消しは更新後の一覧も返すので、クライアントは往復1回で描画し直せます。
不正な `subject` / `action` は400、1分あたり20件を超える投稿は429を返します。
`action` は対象が `queue` のときだけ待ち人数（`empty`/`short`/`medium`/`long`）を受け付け、
それ以外では在庫の状態（`available`/`low`/`unavailable`/`refilled`）のみを受け付けます。

## いつ切れやすい？（曜日×時間帯のリズム）

直近4週間の投稿を曜日×時間帯（平日・開放時間）に集計し、「作れる／切れがち」の傾向を
ヒートマップで、混み具合を行列投稿の時間帯別バーで可視化します。判定は全投稿を
良し悪しに分類（作れた・十分ある・補充＝緑側／作れなかった・ない・残り少なめ・故障・
清掃中＝赤側）。「要注意タイム」「ねらい目」はデータから自動導出です（`shared/rhythm.ts`、
ユニットテストで固定）。

赤緑の配色は色覚多様性で潰れやすいため、色だけに頼らない設計にしています: 赤側の濃い
2段には斜線テクスチャ、凡例に ✓/× 記号、全セルに件数入りのツールチップ（aria-label 兼用）。
ダークモードは同じ発散配色を暗地用に組み直し、悪化側ほど明るく浮くアンカーです。
投稿が少ないセルは薄く、判定材料が全体で20票未満の間はカード自体が「投稿がたまると
表示されます」の空状態になります。

## 元のデザインとの違い

`project/4F Drink Status.dc.html` のプロトタイプを実装したものです。見た目は踏襲していますが、
以下は意図的に変えています。

- **保存先** — localStorage から D1 へ。投稿がラウンジ全体で共有されるようになりました。
- **投稿者** — 固定のダミーから、署名付き匿名IDへ。
- **「このアプリについて」の文面** — Azure 前提の記述を、実際の構成（Cloudflare）に合わせました。
- **デザインツールのツマミ** — マシンの絵の表示と集計ウィンドウは `shared/config.ts` の定数に固定。
  ヘッダーの自動更新 ON/OFF だけは操作できるままにしています。

ヘッダーの「デモ」バッジは `src/components/Header.tsx` の `BADGE` を `null` にすると消えます。
